# Part A — 架构与基础概念

## 1. TPU/NPU 在异构系统里是什么

**TPU / NPU**（下文统称 TPU 类加速器）是为 **稠密线性代数 / 卷积类算子** 定制的域专用加速器（DSA），不是「缩小版 GPU」。

| 角色 | 擅长 | 不擅长（通常） |
|------|------|----------------|
| CPU | 控制流、OS、稀疏/不规则、小批量 | 大规模 GEMM 能效 |
| GPU | 可编程并行、训练生态、动态 shape/新算子 | 固定算子下的极限能效与面积效率 |
| TPU/NPU | 矩阵乘加为主路径上的吞吐与能效 | 强分支、强发散、频繁换模型拓扑时的灵活性 |

面试里一句话定位：

> TPU 把「算什么」尽量在编译期/图编译期钉死，硬件用 **数据流 + 大片 MAC 阵列 + 显式片上缓冲** 把数据喂满；GPU 把「怎么并行」留给 SIMT 编程模型与调度器，用延迟隐藏吃掉访存等待。

术语注意：业界 NPU / AI 加速器 / 推理芯片命名很杂；架构讨论时盯 **执行模型 + 存储层次 + 编程/编译模型**，不要被产品名带偏。

## 2. 典型子系统框图（面试可画）

下面是一张「多数公司都能对上号」的抽象图（具体名字因家而异）：

```text
                    ┌──────── Host (CPU / OS) ────────┐
                    │  Runtime / Driver / Compiler     │
                    └──────────────┬──────────────────┘
                                   │ PCIe / C2C / 片上总线
                    ┌──────────────▼──────────────────┐
                    │  控制面：Cmd Queue / MCU/微码    │
                    │  中断、门铃、fence、固件加载      │
                    └──────────────┬──────────────────┘
           DRAM/HBM ◄── DMA/NoC ──┤
                    ┌──────────────▼──────────────────┐
                    │  片上 SRAM / Unified Buffer      │
                    │  (activation / weight / psum)   │
                    └──────────────┬──────────────────┘
                                   │  高带宽、短距离、常多 bank
                    ┌──────────────▼──────────────────┐
                    │  计算阵列：MAC / Systolic / MXU  │
                    │  (+ 向量/激活/归一化等附属单元)   │
                    └─────────────────────────────────┘
```

画图时务必标出两条面：

| 面 | 典型内容 | 底软关心什么 |
|----|----------|--------------|
| **控制面** | 门铃、命令队列、descriptor、中断、状态寄存器、固件 | ioctl / mmap / IRQ / reset / 超时回收 |
| **数据面** | DMA、NoC、SRAM bank、阵列读写口 | 带宽、对齐、bank 冲突、与计算的重叠 |

**本节要点**：TPU 子系统 = 控制面调度 + 显式数据搬运 + 阵列计算；面试时先画这三块，再往下钻。

## 3. 脉动阵列与「算力」从哪来

**脉动阵列（Systolic Array）** 的核心直觉：数据在 PE（Processing Element）之间 **规律地脉动传递**，每个 PE 做 MAC，减少对全局存储的反复读写。

- 峰值算力粗算：`TOPS ≈ 2 × (#MAC) × freq`（乘加算 2 ops；具体是否算 sparse/结构化要看口径）。
- 真正跑满的前提几乎总是：**操作数按时出现在阵列边界**，且 partial sum / 结果有地方写。
- 所以架构矛盾常落在：**阵列很宽 vs 片外带宽有限 vs 片上 SRAM 容量有限**。

附属单元（向量 ALU、激活、Pooling、Norm、Transpose/Im2col 引擎等）决定「非 GEMM 尾巴」会不会把整网拖成带宽或标量瓶颈——三/四面常问「算子不全落阵列时系统怎么办」。

**本节要点**：算力是面积×频率堆出来的；**可持续算力**由数据供给与复用决定。

## 4. 数据流三件套：WS / OS / IS

「数据流」回答：**谁驻留在 PE/本地寄存器里，谁在流动**。经典三分法（Eyeriss 谱系常考）：

| 类型 | 驻留（相对不动） | 流动 | 直觉 |
|------|------------------|------|------|
| **WS** Weight Stationary | 权重 | 输入/激活流过，psum 累加或流出 | 权重复用高；推理常见 |
| **OS** Output Stationary | 输出部分和 | 输入与权重流入 | 减少 psum 来回写；利于累加精度路径 |
| **IS** Input Stationary | 输入/激活 | 权重流过 | 输入复用高的场景 |

没有绝对最优：取决于 **复用模式、SRAM 切分、是否卷积/GEMM、量化位宽、batch**。  
编译器 / 映射器的工作，很大一部分就是：**选数据流 + 选 tiling + 生成 DMA 与计算发令顺序**。

底软侧你未必手写数据流，但必须能解释：

- 为何换一种 stationary，DRAM traffic 会变；
- 为何「硬件很强、模型一换利用率崩」——往往是映射与缓冲切分不匹配，而不只是驱动 bug。

**本节要点**：数据流 = 复用策略的硬件化；性能讨论要从「谁复用、复用几次」开口。

## 5. 与 GPU 最主要的区别

三/四面不要铺陈 CUDA API，抓 **执行模型 / 存储 / 延迟策略 / 软件入口** 四条主线即可。

### 5.1 对照总表

| 维度 | GPU（典型） | TPU/NPU（典型） |
|------|-------------|-----------------|
| 执行模型 | SIMT：大量线程，warp 调度 | 数据流 / 阵列：算子或 tile 级推进 |
| 延迟策略 | 大量并发上下文 **隐藏** 访存延迟 | **显式搬运 + 流水重叠** 把数据提前就位 |
| 片上存储 | 寄存器 + shared + L1/L2（硬件缓存语义强） | **Scratchpad / 多 bank SRAM** 为主，地址与生命周期更「编译期可见」 |
| 编程入口 | Kernel（CUDA/HIP 等）+ 运行时调度 | **图 / IR → 编译映射** + 命令队列；内核态常更「设备作业」 |
| 灵活性 | 新算子、动态控制流友好 | 固定/半固定算子路径上能效与密度高 |
| 能效/面积 | 为通用并行付税 | 为 GEMM 类路径少付税 |
| 一致性 | GPU 内存模型 + 驱动/运行时；异构时仍要处理 host 可见性 | 常是 **DMA + 显式同步**；与 CPU cache 的维护责任更「暴露」 |

### 5.2 最值得开口的三句

1. **GPU 用「人多」扛延迟；TPU 用「把路铺好」躲延迟。**  
2. **GPU 的 shared memory 像可编程缓存；TPU 的 UB/SRAM 更像编译器分配的暂存器堆。**  
3. **GPU 生态赢在可编程；TPU 赢在既定模型上的每瓦每毫米吞吐——所以编译器与 DMA 调度是一等公民。**

### 5.3 容易混淆的点

- 现代 GPU 也有 Tensor Core，会「看起来像小型矩阵单元」——但周围仍是 SIMT + 缓存层次；**整体执行模型仍是 GPU**。
- 有的 NPU 带小 CPU/DSP/向量核，负责不规则部分——系统仍是异构，别把整片都说成纯阵列。

**本节要点**：差异在模型与存储语义，不在「有没有矩阵单元」这一表面特征。

## 6. 底软视角的软件栈分层

面试「你负责哪一层」时，用这张表对齐语境：

```text
模型 / 框架 (PyTorch, ONNX, …)
        ↓
图编译 / 算子选型 / 内存规划 / 调度 (常用户态)
        ↓
Runtime：stream/queue、异步、多设备、内存池
        ↓
Kernel Driver：设备节点、ioctl、mmap、IRQ、复位、固件、电源
        ↓
Firmware / MCU：解析命令、kick DMA、kick 阵列、报完成/错误
        ↓
RTL：队列、DMA、SRAM、阵列、NoC
```

底软高频责任（三/四面仍可能深挖）：

| 主题 | 典型问题 |
|------|----------|
| 设备生命周期 | probe、固件加载失败、复位、热升级、多开 |
| 命令模型 | 同步 ioctl vs 异步队列；doorbell；完成中断 vs poll |
| 内存 | CMA/ION/dmabuf、设备 VA、IOMMU、大页、连续 vs scatter |
| 同步 | fence、跨引擎依赖（DMA→Compute→DMA）、超时与抢占（若有） |
| 可观测 | 利用率计数器、带宽计数、挂死抓现场 |

与 GPU 驱动对比的一句话：GPU 驱动很重（调度、显存、上下文）；TPU 驱动往往 **更「薄」但更「硬」**——薄在少做通用调度，硬在错误路径、一致性、以及和编译产物/固件契约不能错。

**本节要点**：底软处在「把编译器的意图变成硬件可执行的作业流」；契约清晰比功能堆叠更重要。

## 7. Roofline：先分清算力墙还是带宽墙

Roofline（屋顶线）帮助你避免空谈优化：

```text
实际性能 ≤ min( 峰值算力, 算术强度 × 可达带宽 )
算术强度 ≈ 有效运算量 / 片外字节流量
```

- **算力墙**：阵列吃不饱通常不是「MAC 不够」，而是指令/发令/同步太碎，或附属单元拖后腿。  
- **带宽墙**：tile 太大/太碎、复用差、反复写中间结果到 DRAM。  
- **平衡点**：提高算术强度（融合、驻留、量化减字节）或提高有效带宽（更好 DMA、更少冲突、更好通道利用）。

**本节要点**：优化前先定性瓶颈；Part B 的技术都是在推高「有效强度」或「有效带宽」。

# Part B — 数据流传输与性能细节

## 8. 有效吞吐公式：别只盯峰值 TOPS

端到端某一层/某一 job 的有效表现，可拆成：

```text
有效吞吐 ≈ 峰值算力
          × 阵列利用率
          × (有效计算时间 / 墙上时钟)     ← 重叠与空等
```

「数据流传输性能」通常同时影响后两项：

- 数据没就位 → 利用率低；  
- 等 DMA / 等中断 / 等 host → 墙上时钟被拉长。

所以面试官问「怎么提升数据传输性能」时，完整答案应覆盖：

1. **减少必须传输的字节**（复用、融合、量化、压缩）；  
2. **提高链路与 DMA 的有效带宽**（对齐、burst、多通道、少冲突）；  
3. **用重叠把传输藏进计算**（双缓冲、多队列、软硬流水）。

**本节要点**：传输优化 = 少搬 + 快搬 + 搬的时候别让阵列闲着。

## 9. 层级与复用：让数据少跑 DRAM

典型层次（名称各异，角色类似）：

| 层级 | 角色 | 软件/编译可见性 |
|------|------|-----------------|
| DRAM/HBM | 容量池、最终真相 | 分配、钉扎、IOMMU 映射 |
| NoC / 总线 | 共享带宽、仲裁 | QoS、多 master 争用 |
| 片上 SRAM（多 bank） | 工作集、双缓冲舞台 | tiling、bank 映射 |
| PE 局部寄存器/脉动链路 | 最高复用 | 数据流选择 |

**复用**是降低 DRAM traffic 的第一性原理：同一权重/激活被多少 MAC 吃到，算术强度就上去。  
WS/OS/IS、卷积的 loop nest 交换、weight 常驻，都是复用策略。

经验口径（口述用）：

- 中间激活 **进进出出 DRAM** → 多半先查融合与 SRAM 规划；  
- 权重每个 layer 只读一次但仍带宽爆炸 → 查位宽、压缩、是否过度重新排布；  
- NoC 打满但阵列空 → 查 bank 冲突、端口竞争、描述符过于琐碎。

**本节要点**：最快的传输是「不用传」；其次才是「传得快」。

## 10. Tiling / 双缓冲 / 流水重叠

### 10.1 Tiling（分块）

把大张量切成能放进 SRAM 的块：

- 块太大：装不下，被迫回吐 DRAM；  
- 块太小：DMA 启动开销占比高，阵列发令频繁，利用率差；  
- 块形状：要同时照顾 **阵列几何**（比如 128×128 MAC）与 **DRAM burst / bank**。

### 10.2 双缓冲（Ping-Pong）

经典套路：SRAM 划两块（或逻辑上两套 buffer）——

```text
时间片 t:   DMA 填 BufA 时，阵列吃 BufB
时间片 t+1: DMA 填 BufB 时，阵列吃 BufA
```

目标：`T_dma ≈ T_compute` 时墙上时间 ≈ `max(T_dma, T_compute)`，而不是相加。  
若 `T_dma` 系统性更大 → 仍是带宽墙，双缓冲只能掩盖到 `max`，不能创造带宽。

### 10.3 更深流水

不止 DMA∥Compute，还可：

- Host 提交 ∥ 设备执行（命令队列深度）；  
- 多 DMA 引擎：一边搬 weight、一边搬 activation；  
- 多核/多 cluster：前一层结果直送下一 cluster（片上转发），避免 round-trip DRAM。

**本节要点**：双缓冲是「重叠」的标配故事；面试要补一句「重叠消不掉瓶颈类型，只改变墙上时间构成」。

## 11. DMA 与描述符：底软真正能动的旋钮

编译器决定「搬什么」；驱动/固件/DMA 编程决定「搬得是否像样」。

### 11.1 描述符链与批量

| 做法 | 收益 | 风险/代价 |
|------|------|-----------|
| 单笔同步 DMA | 实现简单 | doorbell/IRQ 过频，CPU 与设备都忙于握手 |
| Descriptor list / SG 链 | 一次 kick 多段，提高硬件利用率 | 准备成本、错误定位更难 |
| 环形队列 + 多 in-flight | 深度重叠 | 需要严格完成序 / fence 语义 |

### 11.2 Burst、通道、并行

- 尽量长 bust、顺序地址，吃满 AXI/CHI/NoC 的有效带宽；  
- 多通道交织（按 bank/channel interleave）要与物理地址映射一致，否则「看起来并行、实际打到同一 channel」；  
- 读写比、单向饱和：有的链路写应答或读返回路径先满。

### 11.3 与计算的契约

设备侧常见模型：

```text
Cmd:  LOAD_TILE → GEMM_TILE → STORE_TILE → … → FENCE → IRQ
```

底软要保证：

- LOAD 完成可见后再 kick GEMM（硬件依赖或软件 fence）；  
- STORE 完成对 host/下一引擎可见；  
- 错误时哪一层负责停流、drain、复位。

**本节要点**：DMA 优化不是「memcpy 更快」，而是 **批量、对齐、多 in-flight、与计算依赖最小化**。

## 12. 一致性、对齐、跨界：静默吞性能的坑

这些题最能区分「用过设备」和「只看过架构图」。

### 12.1 CPU cache 与设备 DMA

若 host 准备的权重/输入在 **cacheable** 内存：

- 设备读前：CPU 侧需 **clean**（把脏数据推到点对点一致点）；  
- 设备写后 host 读：CPU 侧需 **invalidate**；  
或使用 **non-cacheable / 流式 DMA API / dmabuf 约定** 把责任收进框架。

细节与总线属性见 [`05-bus-rtl/02-cache.md`](../05-bus-rtl/02-cache.md)、[`01-kernel/02-memory.md`](../01-kernel/02-memory.md)。  
性能角度：频繁小块 sync 会把 CPU 和总线打满；应 **大批次、少同步点**。

### 12.2 对齐与 4K 边界

- 描述符、缓冲起始对齐不够 → 硬件拆单、短 burst、甚至走慢路径；  
- SG 表、IOMMU 页：跨页本身正常，但 **过多碎片** 会增加 TLB/翻译与描述符压力；  
- AXI 单笔 burst 不跨 4K 等规则，会影响 DMA 引擎切分（见总线专文）。

### 12.3 Bank 冲突与端口争用

片上 SRAM 多 bank：同一周期多端口打到同一 bank → 冲突气泡，阵列侧表现为「数据口饿死」。  
映射策略（编译器）+ 有时运行时重排，都是传输路径的一部分。

**本节要点**：传输性能问题里，有一类根本不是「DRAM 规格不够」，而是 **同步过频、拆单过碎、冲突过多**。

---

## 13. 算子融合、量化、调度：少搬一次就多一分

### 13.1 算子融合（Fusion）

`Conv + Bias + Activation` 若不融合：中间张量可能写回 SRAM 甚至 DRAM，再读出。  
融合后：中间值留在流水线或局部缓冲。  
这是 **架构+编译** 题，但底软要能解释：融合后命令粒度变大、错误归因更难、内存寿命更短。

### 13.2 量化与压缩

INT8/INT4/FP8 等直接减字节；权重压缩/稀疏（若硬件支持）减 traffic。  
代价：精度、重排开销、以及 decode 单元是否成为新瓶颈。

### 13.3 调度与批处理

- **Batch**：抬高复用与阵列利用率，但抬高延迟与 SRAM 压力；  
- **多流/多队列**：提高设备占用，但引入公平性与死锁/依赖复杂度；  
- **跳过 host**：能在设备上串起的依赖，不要每步踢回用户态。

**本节要点**：系统性能常赢在「图级少搬」；传输引擎再强，也救不了每层都打满 DRAM 的图。

---

## 14. 瓶颈归因清单（三/四面口述骨架）

被问「性能上不去怎么查」时，建议按层说，而不是丢工具名：

| 层级 | 看什么 | 典型结论 |
|------|--------|----------|
| 墙上 vs 设备忙 | host 提交间隙、同步过多 | 队列深度不足 / 同步粒度过细 |
| 阵列利用率 | MAC active 周期比 | 数据没就位或 tile 形状不匹配 |
| DRAM/HBM 带宽 | 读写利用率、页策略 | 复用差或访问模式差 |
| NoC/DMA | 通道饱和、重试、描述符速率 | 冲突、对齐、拆单 |
| 一致性/CPU | sync 耗时、IPI/软中断 | cache 维护过频 |
| 精度/正确性路径 | 是否走了通用慢路径 | 附属单元或 fallback |

一句话收束：

> 先用 Roofline 定性算力墙还是带宽墙，再用「少搬 / 快搬 / 重叠」三条去对症；底软保证契约与 DMA 质量，编译器决定复用与融合，硬件决定峰值与端口。

---

## 小结

1. TPU 类加速器是 **数据流 + 显式存储 + MAC 阵列** 的 DSA；和 GPU 的根本差别在执行模型与延迟应对策略。  
2. WS/OS/IS 描述的是复用谁；复用决定片外流量，进而决定能不能接近峰值 TOPS。  
3. 底软栈是 **驱动/固件把作业流可靠送进硬件**；异步队列、DMA、一致性、错误回收是核心。  
4. 传输性能 = 少搬（融合/量化/驻留）+ 快搬（DMA/对齐/bank）+ 重叠（双缓冲/多 in-flight）。  
5. 三/四面表达：先画框图与控制/数据面，再用 Roofline + 分层归因，最后落到你负责层的旋钮与契约。
