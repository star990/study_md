## 一、真题记录

### Q1. 如何在帕拉丁上分析定位长时间偶现的小概率问题？

- **出处**：CV 相关面试；开放性追问
- **原题**：如何在帕拉丁（Palladium）上分析、定位长时间偶现的小概率问题？
- **追问 / 实际场景**：AI 芯片大量算子运算；帕拉丁跑一天后才发现精度不够——其中可能只有几笔数据 DMA 搬运有误；**什么时候错完全不清楚**，很难定位，也**抓不到出问题的第一现场**。
- **当场要点**（整理自口述）：
  1. **总原则**：不论芯片仿真还是别的工业产品，小概率问题的宗旨都是——让偶现变必现，或显著提高复现概率。
  2. **查变更**：软件 / RTL 最近修改 log，是否有可疑相关改动。
  3. **看规律**：复现是否有时间、结果等多维度规律；有则榨取可继续分析的信息。
  4. **拆 case**：大 case 能否拆成小 case；把复杂条件打散，聚焦真正影响结果的条件。
  5. **造 trigger**：出错时 trigger，用帕拉丁抓波。
  6. **加压 / 更严 case**：理解测试本身，正向制造比原 case 更严的压力测试；若能加速复现，需再确认 root cause 是否与原问题一致——一致则赚到，不一致则继续分析。
- **参考答 / 自评**：
  - 前半「提概率 + 拆条件 + trigger 抓波」方向正确，面试官认可的框架感够用。
  - 追问把难点钉在：**结果晚到、第一现场已过、无法用「出错瞬间 trigger」**。这时单靠「出错再抓」不够，要把答案升级到「事后可回溯 / 可二分 / 可对比」的手段（见第二块）。

## 二、盲区延伸

### 由 Q1 → 偶现问题的通用闭环（可答开放性题的骨架）

用四步说清，比罗列技巧更稳：

| 步骤 | 目的 | 例子 |
|------|------|------|
| **提概率** | 偶现 → 高频 / 必现 | 加压、边界、随机种子扫、拉长运行但收窄刺激面 |
| **缩范围** | 全系统 → 可疑子系统 | 查变更、拆 case、按算子/阶段/通道隔离 |
| **造证据** | 从「感觉不对」→ 可对比的痕迹 | 中间结果 checksum、golden、环形 trace |
| **逼近现场** | 从「跑完才知错」→ 尽量靠近首次出错点 | 检查点二分、save/restore、延迟 trigger、离线回放 |

当场答完「提概率」后，主动补一句：**若错误只在长跑结束才暴露、抓不到第一现场，就转检查点 + 中间比对 + 回溯**，正好接住追问。

### 由 Q1 追问 → 「精度不够 / 几笔 DMA 错」且不知何时错

场景本质：**故障窗口极短、观测窗口极晚**（一天后才发现精度差）。帕拉丁波形深度有限，不能假设「发现错误时还能看到出错那一拍」。

可答的几条线（按性价比排序，面试口述选 3～4 条即可）：

1. **中间结果落桩，把「一天后」改成「第 N 步」**  
   按算子 / graph 阶段 / batch / tile 输出做 checksum、CRC、或与软件 golden / 上一版比特比对。精度差一旦出现，立刻知道**最早失败的阶段**，再在该阶段内加密比对粒度。

2. **时间轴二分（检查点 / save-restore）**  
   长跑按墙钟或算子进度打 checkpoint。发现最终精度差后，从中点 restore 续跑：中点已坏 → 错在前半；中点仍好 → 错在后半。把「一天」收成「一小时 / 一个算子」再谈抓波。  
   （帕拉丁 / 仿真环境若支持 snapshot、加速器侧若支持状态 dump，都归这类。）

3. **环形 / 滚动 trace，专门对付「不知何时」**  
   无法预知 trigger 时：持续记录关键 DMA 描述符、地址、长度、id、少量 data fingerprint 到环形缓冲；精度校验失败时**冻结缓冲**——即使错过第一现场，仍保留失败前一段轨迹。波形同理：rolling dump + 失败时 stop。

4. **软件侧先判「哪几笔」再下硬件**  
   AI 场景优先回答：先定位是哪个算子、哪次 DMA、哪块 buffer 与 golden 不一致（host 侧 log / 比对），再针对该笔配置 trigger（特定 addr/len/id、desc 匹配）。否则在「全天任意一笔」上设 trigger 等于没有。

5. **加压与「是否同因」**  
   加压（更密的 DMA、更极端对齐、背压、乱序、多 master）用来提概率；一旦加压能复现，必须用同一套中间比对确认失败签名与原长跑一致，避免修了一个「压力特有 bug」。

6. **变更与配置对照**  
   长跑偶现也常落在：近期 RTL/驱动/算子库改动、某配置组合、某数据分布。先对齐「上次好 / 这次差」的 diff，再决定要不要上满配抓波。

### 由 Q1 → 答题时易漏的一句（针对帕拉丁）

- **Trigger 抓波**依赖「能定义出错条件」；追问场景恰恰是条件未知 → 先用软件/中间比对定义条件，再 trigger。  
- **波形不是唯一证据**：checksum、desc log、checkpoint 在长跑里往往比「开一天全波形」现实。  
- 面试官要听的是：**你会不会在抓不到第一现场时换策略**，而不是只会说「再跑、再抓」。

## 小结

1. 小概率问题总原则：提复现概率，再缩范围、造证据。  
2. 「查 log → 看规律 → 拆 case → trigger 抓波 → 加压」是合格骨架；追问点在**结果滞后、无第一现场**。  
3. 滞后场景优先：**阶段/算子级比对 → 检查点二分 → 环形 trace 冻结**，最后才是精确 trigger 抓波。  
4. 加压能复现时，务必确认与原失败同一 root cause。  
5. 下次口述可收成：提概率 → 缩范围 → **中间可见性** → 逼近第一现场。
